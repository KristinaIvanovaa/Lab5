## REST API

Каждая сущность доступна по `/api/plays`, `/api/theatre-halls`, `/api/performances`, `/api/users` и `/api/tickets`: список и получение по ID (`GET`), создание (`POST`), частичное изменение (`PATCH`) и удаление (`DELETE`).

Бизнес-операции (`/api/operations`):

1. `POST /tickets/{id}/purchase` — покупает только зарезервированный билет на предстоящее запланированное представление и фиксирует текущую цену.
2. `POST /tickets/{id}/cancel-reservation` — отменяет только резервацию до начала представления.
3. `POST /tickets/{id}/refund` — фиксирует возврат купленного билета до начала представления; статус становится `REFUNDED`, цена покупки сохраняется.
4. `POST /performances/{id}/cancel` — отменяет предстоящее запланированное представление: резервации становятся `CANCELLED`, купленные билеты — `REFUNDED`.
5. `PATCH /performances/{id}/reschedule` — переносит представление на будущее время, только если новый интервал свободен в том же зале.

Билеты создаются только в статусе `RESERVED`; менять статусы через CRUD нельзя. Новые представления должны быть будущими, а занятые интервалы одного зала не могут пересекаться. Изменения бизнес-операций выполняются транзакционно. Ошибки ввода возвращаются как `400`, отсутствующие записи — `404`, недопустимое состояние или занятое место/время — `409`.

## Аутентификация и авторизация

`POST /auth/register` создаёт активную учётную запись CUSTOMER и выдаёт JWT-пару. `POST /auth/login` проверяет email и пароль и выдаёт пару, `POST /auth/refresh` принимает `{"refreshToken":"..."}` и обменивает активный refresh на новую пару. Старые refresh-сессии остаются в таблице `user_sessions` со статусами `USED` или `REVOKED`. Ответы login/register/refresh содержат `accessToken` и `refreshToken`; access также передаётся в заголовке `Authorization: Bearer ...`. Маршрут регистрации `/api/auth/register` сохранён как псевдоним.

Для защищённых запросов используйте Bearer access-токен. HTTP Basic продолжает поддерживаться. Пароль регистрации должен содержать не менее 12 символов, строчные и заглавные латинские буквы, цифру и спецсимвол; пароль хранится в BCrypt. Роль регистрации задаётся сервером.

Обе разновидности токена подписаны HS256, имеют `sub`, уникальный `jti`, `iat`, `exp` и `type`. Сроки задаются переменными `JWT_ACCESS_TOKEN_TTL_SECONDS` (по умолчанию 900) и `JWT_REFRESH_TOKEN_TTL_SECONDS` (по умолчанию 604800). Для развёртывания задайте собственный секрет `JWT_SECRET` длиной не менее 32 байт; значение по умолчанию предназначено только для локальной разработки. Создайте `user_sessions` из `db/init.sql` до запуска приложения.

Получите CSRF-токен через `GET /api/auth/csrf` и передавайте `token` в заголовке `X-CSRF-TOKEN` для защищённых POST, PATCH и DELETE. Эндпоинты `/auth/*` и регистрация не требуют CSRF-токена.

| Возможность | CUSTOMER | ADMIN |
|---|---|---|
| Просмотр спектаклей, залов и представлений | Да | Да |
| CRUD спектаклей, залов и представлений | Нет | Да |
| Создание билета | Только себе | Да |
| Просмотр своего билета, покупка, отмена резервации и возврат | Да | Да |
| CRUD билетов, управление пользователями, отмена и перенос представления | Нет | Да |

Администратора создают вручную, чтобы регистрацией нельзя было получить повышенные права: зарегистрируйте учётную запись и выполните `UPDATE users SET role = 'ADMIN' WHERE lower(email) = lower('<email>');` от имени владельца базы. Администратор может отключить учётную запись через `PATCH /api/users/{id}` с `{"enabled":false}`. Для старой БД выполните:

```sql
ALTER TABLE users ADD COLUMN password_hash VARCHAR(60) NOT NULL DEFAULT '';
ALTER TABLE users ADD COLUMN role VARCHAR(20) NOT NULL DEFAULT 'CUSTOMER';
ALTER TABLE users ADD COLUMN enabled BOOLEAN NOT NULL DEFAULT TRUE;
CREATE UNIQUE INDEX uk_users_email_lower ON users(lower(email));
```

В Postman задайте переменные коллекции `adminEmail` и `adminPassword` для администратора. Коллекция автоматически регистрирует CUSTOMER, получает CSRF-токен, демонстрирует успешный просмотр и отказ `403`. Основной сценарий CRUD и бизнес-операций выполняется от имени ADMIN.
